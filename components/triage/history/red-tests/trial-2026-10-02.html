Does the triage engine work outside the atlas?

The plan session triaged the 34 red test suites on main by hand: four readers each ran their suites and found causes (team/handoffs/2026-10-02-red-tests-triage.md, e9995982a). The triage engine then ran blind on the same 34 suites, at the same commit, using only the failing lines, the code and a one-page definitions file for this domain. Three Claude agents ran in parallel, about 10 minutes each, and none of them read the plan session's note. This page scores the engine against that hand triage.

The score
26agree outright
4same fix, different label

2differ: genuine judgment difference

So 30 of 34 lead to the same action as careful hand triage, and the 2 differences are judgment calls where either reading is defensible. The plan session's environment verdicts are soft ground truth: each suite was run once.

What this says about a general component

The engine carries over

The same passes worked on a list with nothing in common with component issues except shape: still true, cause, the one action that clears it, priority, lane. Only the definitions file was new.

The definitions file is where it goes wrong

All 4 "same fix, different label" cases trace back to one line I wrote: "a card awaiting approval is a ruling". Cause and blocker are different things. The general component should keep them separate: a cause class, plus a blocked-by field (an unapproved card, or a decision).

Shared causes, found blind

The engine found the same shared causes as the plan session: the 09-30 brand-folder move behind the 4 review suites, the owner's restore commit behind 3, the second worker slot's file behind 2, and one approval (WM-106) clearing 2 suites. That is the "clears with N" count working in a second domain.

It also found new things

The test reporter sometimes records a misleading first failing line: twice the line it showed was not the real failure. Approving WM-106 must also cover team/plans/*.md, or both of its suites stay red. And the restore-commit bug is not live today, so it isn't urgent: only two run requests exist, both from before the break.
