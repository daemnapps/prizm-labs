One engine, a pack per theme

Every list that gets triaged is a theme, with its own owners, priorities and flow. Each theme is described in one pack, curated by its triage owner, and runs through the same core engine. The atlas comes first because it's the one worked out today. Red tests are the second pack, there to prove the shape fits.

The rule: the core never names a person, a path, a cause class or a priority rule. All of that comes from the pack. Changing how one theme is triaged is its triage owner's edit to the pack; changing how every theme is triaged is the team's edit to the core. The walls bind every theme, and no pack can relax one.

How the pieces fit

The packs side by side

Every pack has the same 27 fields. A field that doesn't apply is kept, set to nothing with a reason, so the core can always tell "not applicable" from "forgotten". Rows in amber are gaps.

What changes in today's code

The page renderer

  • The list of people, the summary labels, the weights and the age cap come from the pack.
  • So do the paths for summaries, drafts and decisions.
  • "Issue" in the explain prompts becomes the pack's item word.

The atlas triage script

  • Its whole pass becomes the atlas adapter plus themes/atlas.json.
  • Its "themes" are renamed "categories", so the two words never clash.

The red-test definitions

  • Become themes/red-tests.json.
  • The prose stays as its explanation.
  • The trial's hand-reading becomes a small adapter.

About a day of work in the atlas stream's own area once the contract is agreed (inferred).

The third-theme test, and when to change course

Atlas issues and red tests are both "something is broken" lists. The parked cards (127) are a "still wanted?" list: no fix, just keep, retire or re-scope. If they run through the core with only a new pack and adapter, the core is general. If the core itself has to change, the contract is missing something, most likely a second item shape for decisions. Either way, record which.
