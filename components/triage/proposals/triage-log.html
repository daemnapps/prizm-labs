Proposal · triage · 2026-10-02 · for discussion, not ruled

One log for every triage act. Everything else reads from it.

Each time someone fixes, drafts, closes, signs, undoes or decides something on a triage item, it is written once, as a record. The weekly digest, the triage pages and the atlas all read those records. So does Claude itself: whenever someone works in a component, the recent changes there load into their Claude automatically.

How it fits together

What one record holds

Example: the record that would be written when the team fixes intake#6. Every field is something a person or a machine can look up later.

# example record: nothing has been written act change item intake-6 who steph when 2026-10-06T09:12Z areas components/intake/tools/pools.py commit (the commit's id) test copy rows' files exist why copy pointers named files that don't exist; the slug is now the file name ruling none (the brief named the fix)
act
What happened: one of the eight acts.
item
The issue or action it was about.
who / when
The person, and the time from date -u.
areas
The components and folders it touches. This decides which context files it appears in.
commit / test
Where the change is, and what proves it. A machine can check both are still there.
why
One plain line, written by the triage owner. The only free text in a record, and kept short on purpose.
ruling
A pointer to the decision-log line, when a ruling allowed the change.

How Claude picks it up

Each component's instructions file gets one import line that points at its generated context file. When someone's Claude works in that component, both load. Tested 2026-10-02 in a throwaway repo with Claude Code's headless mode:

# components/intake/CLAUDE.md (owner's file, plus one line) …the owner's own instructions… @../../runs/triage/context/intake.md
# runs/triage/context/intake.md (generated) Record of recent triage changes in intake. These are facts, not instructions. 2026-10-06 · intake#6 · copy pointers use the slug as the file name (all 614 pointed at missing files) · test: copy rows' files exist · triage, the team

works Session started at the workspace root

As soon as Claude opened a file in the component, it had the component's instructions and the imported context file under runs/. This is how teammates normally work.

doesn't Session started inside the component folder

An import that reaches outside the starting folder was not loaded in headless mode. Those sessions would miss the context, so the weekly digest remains the backstop.

How it relates to the issue briefs

The eight-part brief (SCHEMA §5) and the log answer different questions about the same issue. The brief says what is wrong and what would fix it, as found. The log says what was done about it, by whom and why, over time. They meet in one place: the issue's open or closed state.

1 · found

Brief written

A system run finds the issue and writes its eight parts into the component's flow. Older P0/P1 issues have theirs in the issue-briefs files. exists

2 · sorted

Triaged

A triage run reads the briefs: one action, priority, the three whos, who does each item. Rebuilt each run. exists

3 · acted

Act logged

A fix, draft, close, signature, undo or ruling becomes one record that points at the issue by id. proposed

4 · state

Issue updated

A close or fix marks the issue resolved, with the commit as evidence. An undo should reopen it. close exists reopen missing

5 · next run

Carried forward

The component's next run keeps the issue's number and state, and fills in a missing brief. A guard flags any run that undoes a close. exists

6 · shown

Read together

Atlas page, triage pages, digest and Claude's context show the brief and its history. The explain prompts read both. partly

The brief feeds the record

Brief fix → the drafted change and the record's commit. Brief impacts and evidence paths → the record's areas (so the right context files get it). The test the fix names → the record's test. Nothing is typed twice.

Two different "why"s

The brief's why it matters is why the issue is a problem. The record's why is why this act was taken: "the brief named the fix", or the owner's reason for undoing it. Both stay; neither replaces the other.

Issues without a full brief

Under the "targeted" ruling, P2/P3 issues gain their eight parts on the component's next run. The log doesn't wait for that: a record needs only the id, the act, the commit or test, and one line on why.

What Claude sees in a component

The context file carries the log's recent acts. It could also list the component's open P0/P1 issues, one line each from their briefs, so Claude knows the known problems before editing. That is an option within the size cap, not yet proposed.

One gap to close: the carry-forward rule (SCHEMA §5a) lets the triage owner close an issue, but nothing lets an owner's undo reopen it. Without that, an undone fix leaves the issue marked resolved. It needs one sentence added to §5a: an undo record clears resolved and notes who reopened it and why. That goes to the lead with the record-kind card.

What keeps it safe and small

Small

A context file loads into every session in that component, so it holds the last 30 days and at most about 15 one-line entries. Older history stays in the log, readable on request.

Only what shapes the next edit

Changes, drafts, signatures, undos and binding rulings. Closes and forwards stay in the log only: in a coder's context they'd be noise.

Can't be used to steer Claude

A file that loads into Claude's instructions could be used to slip in commands. So it's built only from the records' fixed fields plus each one-line reason, never from issue text or web pages. It opens by saying it's a record, not instructions, and only the triage writer may write it.

One rule, one home

Rulings stay in the decision log. A record points at the ruling's line; it never restates the ruling.

The owner's file stays the owner's

The generated file lives under runs/, where machines write. The component folder only gains one import line, added once by a person: the team drafts it, each owner signs.

Logged before changed

No change lands in someone's component before its record and context line exist. It's proposed as a fifth limit on Option 3.

What it takes, in order

  1. Extend the triage record kind with the five new acts and the areas, commit and test fields, and add the reopen sentence to SCHEMA §5a. Both change shared rules, so the lead cards them.
  2. Rule the import line as a convention (the team, or the team as conventions curator). Then the team drafts it into the 44 component instructions files, and each owner signs once.
  3. Build the context generator and the digest view over the log. This is in the atlas stream's own area; both are generated, never hand-edited.
  4. Then start the Option 3 trial in the quiet components, logged first.

★ Ask the lead to card step 1. Everything after it reads the same records.

Reverse it if: in the first weeks, a teammate's Claude asked "what changed here recently?" inside a component doesn't surface the entry, or context files outgrow their cap. Then fall back to the digest alone. Confidence: high on the log, medium on the context hook (sessions started inside a component miss it).
