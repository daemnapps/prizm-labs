Proposal · not in the atlas yet Component: components/keys Engine owner: Operator B · Definition owner: the ops lead Drawn 29 Sep from manual-nodes.json at HEAD

A small component that holds the names of every key and never a value. It provides one loader every tool uses, the template every key file follows, the register of who holds which key, and checks that file their results as records. The page shows it three ways, each in the atlas's conventions: where it sits on the eight-category chain, its component contract, and one trace, a new key reaching the owner.

This page is hand-drawn in the atlas's visual language, not atlas output. The real atlas shows the component only once its folder exists and its nodes are added to manual-nodes.json.

The four component rules, applied

  1. Three data homes, never mixed. Names and the register live in the component. Values live only in the vendors and each machine's files. Check results land on the plane.So nobody ever needs to open a key file to know what's missing.
  2. Two owner roles, named separately. Operator B owns the loader and checks; the ops lead owns the template and register and approves every change.A new key name is a definition change, so it passes the ops lead's gate like a new metric passes Operator B's.
  3. Consumers touch planes and manifests only. The key health view and /system-ready read results and the approved list, never a key file.Sharing the state of keys widely never means sharing keys.
  4. Engines are machine-agnostic. The loader reads the environment first, so the mini and a laptop run the same code.Four separate loaders today become one.
Kill-conditions, so this stays honest: fewer than about five tools use the loader a month after phase 1 → fold it back into the worker as a helper. A key value ever lands in this folder or on the plane → stop, rotate that key, and fix the check that missed it.
