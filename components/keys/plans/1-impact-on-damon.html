His own setup · not checked
  • Services he's trying, and tools only he uses

  • No approval and no note; never overwritten by the managed file

When checks start: only when a piece of his work enters the system path. /system-fit flags keys read by path or from the Keychain; /system-ready moves them to the shared loader and a company key; /system-review does the same for components already in the workspace. Always on regardless: no key in git or chat, and old shared keys stop working on announced dates.

Supabase also sets what Claude reads

We consolidate data in Supabase first so that Claude, in anyone's session, reads a small set of prepared tables rather than exploring each vendor's whole API. The orders table is the model: the metrics component builds it from each brand's raw store data, one row per order, the same columns for every brand.

Raw, per systemshopify_orders: 56 columns, including customer names, emails and the raw payloadBrand A's and Brand B's own order tables
→
Consolidated by the metrics componentpublic.ordersOne row per order, one set of columns for every brand, revenue in one currency with the original kept beside it (Operator B's sign-off pending). Refreshed by the daily metrics job (MET-C11 (orders chain)).
→
What Claude reads“How many Brand A orders last week, and what revenue?”Answered from orders, the same way for everyone.

Claude exploring the vendor's API

  • Needs the vendor key in the session
  • Every session can define "an order" or "revenue" differently
  • Reaches every field, customer details included
  • Many sessions calling the vendor, each against its rate limit

Claude reading the consolidated table

  • Only a read-only data login
  • One definition, the one the dashboards use
  • Only the columns we chose to prepare
  • One pull, by the sync, for everyone

So for a new data source the question is which prepared table it should feed, not just whether it is synced. Whether the prepared tables leave out customer details is (unchecked); the read-only login could also be limited to prepared tables only (Operator B's call).

For the owner, in practice

What he does

  • Saves the managed file when the ops lead or Operator B send it, once and on each replacement
  • Keeps trials and his own tools however he likes; nobody checks
  • Runs a short smoke test before an old shared key's announced cut-off date
  • When a trial becomes team work, lets /system-ready move it onto a company key. The name stays the same, so his own copy can simply go.

What he stops doing

  • Holding copies of the company's shared keys
  • Lending his OpenAI key to the ops lead
  • Falling back to his personal Apify account
  • Hunting across Keychain, files and the mini for where a key lives
