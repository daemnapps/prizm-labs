# Marketing routing and workflow chains

This is the routing index for agents and marketing briefs. Choose the requested output and maker route here, then read the named skill and the owning component’s CLAUDE.md/CONTRACT.md before acting. Component contracts and existing run records settle implementation details; this index does not replace them. Do not start a workflow merely to answer a question about it.

These are standing business workflows across brands, products, channels and ongoing work. A campaign or moment supplies dates, offers and priorities; Black Friday is the current context, not the boundary of the operating model. Resume the same owning routes for everyday work and later moments. The routes currently mapped here cover marketing; other business functions retain their own component contracts.

## The named workflows

Every deliverable is made by one of these workflows. Each one has a single name, used the same way on every board, page, pack and skill. Each is laid out the same way: what it makes, what goes in, the steps (one component each), what comes out, where a person approves, and which roles do it. ## Distinguish the layers

| Layer | What it means | Source of truth |
|---|---|---|
| Chat lane | Sidebar/session organization, such as VIDEO, COPY or OPS. It does not select a production route. | The session/card’s lane and its session naming instructions |
| Marketing workstream | The deliverable being worked on: video brief, AI video, creator shoot, static ad, email, SMS, storefront or acquisition funnel. | The routing table below |
| Maker route | Who makes a video: `ai`, `creator` or `founder`. A broad `video-ad` display type does not choose this. | Existing run’s route and brief register’s `video-ai` / `video-creator` type; route lock in video-teardown |
| Category, type and format | A content category (Brand), send type (founder-note) and layout format (letter/simple) describe content. They neither establish founder facts nor select AI/creator production. | The brand’s email catalogue; marketing-calendar sets kind/format; identity facts come from position/story |
| Skill | The activation/front door for a job. Read it before the action. | `.claude/skills/<skill>/SKILL.md` |
| Component | The engine owning an operation and its public inputs/outputs. | `components/<component>/CLAUDE.md` and CONTRACT.md |
| Workflow | Ordered component operations and their handoff seams. | This file for routing; owning component/format playbook for execution |
| Stage and checklist | Stage words are the shared display vocabulary; a checklist names evidence needed at a handoff. It does not authorize the next operation. | `components/naming/stages.json`; `components/stage-check/lanes/`; component gates |

## Required routing decision before acting

1. Resolve the brand, requested output, existing brief/run and current stage. Reuse the current record and brief identity.
2. For video, resolve `ai` / `creator` / `founder` from the existing route and assignment. If still unknown and production depends on it, ask once; never default to AI because the asset is video.
3. Name the skill, owning component, input record, expected output, next recipient/system and permitted action. Distinguish inspect, plan, write, produce, package, upload and launch.
4. For creator/founder writing use the existing v1 route loop in video-teardown; AI v2 writing is the video-writing command. Both read prompts from video-writing. The component split is not a second copy of the creative rules.
5. Read the actual skill and contract. A missing front door is reported as a gap; do not invent a skill or substitute an unrelated tool.
6. Route shared helpers (images, cast, briefs/register, file naming, review) back to the parent deliverable. `components/briefs` registers/projects styles; the writing component authors the words.
7. Review evidence and authority for the next action. An inventory row, a checklist tick, an approved brief or a reviewer’s comment does not itself authorize production, sending, spend or deployment. Existing explicit authorization remains valid within its scope.

## Checklist coverage and known gaps

- `naming/stages.json` deliberately groups AI and creator output under Video ad for display. Preserve the maker route separately.
- `stage-check` now resolves the explicit maker route from the brief register and run records. `video.json` checks AI production/edit/card evidence; `video-creator.json` checks creator/founder filming-brief readiness only. Unknown or conflicting routes use `video-unresolved.json` and run no repairs. Creator/founder `--fix` never invokes AI writing or generation. A passing human-brief check does not prove filming, editing or launch.
- SMS and acquisition-funnel building do not have separate matching skills in this checkout. Public component commands and the target repo’s instructions remain the entry points; no new skill is implied by a lane name.
- Email flows and page copy have prompts (`components/email-production/flows/`) but no runner: no code fills or calls them yet, so a flow or page draft is written by following the prompt with its named inputs.
- Role assignment lives in `promo-calendar/definitions/roster.json`: orchestration/design direction and review roles are distinct from the maker route. A named reviewer is not automatically the production assignee.

## Activation and review cycle

1. **Locate and inspect.** The coordinator resolves the brand, current record, requested output and permitted action. Use existing calendar, writing, asset and review records. A request to see a calendar does not regenerate it; a completed email goes to email-review/design, not through the copy writer again.
2. **Plan, then owner review.** `promo-calendar` shows the promo checklist and routes; `marketing-calendar` creates/changes the month only when requested. Show the actual plan and unresolved source facts. Record only the owner’s actual decisions in the owning review surface. A model check is not the owner’s review.
3. **Writing, then owner copy review.** Once plan and writing scope are authorized, activate the matching writing skill for the selected items. Show the actual drafts, their checks and held items. Do not cross into production just because writing files exist.
4. **Production, then review.** After writing/brief review and production activation, use the selected maker route and owning component. The role data in `promo-calendar/definitions/roster.json` identifies orchestration, design direction and reviewers. Keep visual review separate from final activation.
5. **Upload/launch is its own operation.** Use the matching platform gate and the already authorized scope. A generic “activate the workflow” is not `sprint.py --go`: that runner can spend usage, generate pictures and make platform drafts across multiple stages.
6. **Recorded corrections go upstream.** Read the requested Tella transcript, contact sheet and pointed frames; apply concrete corrections to the current work and the highest owning source responsible (brand fact, definition, prompt, engine or skill). Keep provenance and verify the result. Do not rewrite shared definitions when a correction is only an item-specific choice.

The coordinator may delegate independent, authorized lane work to bounded subagents when the environment supports it. Each brief names goal, owner, input record, writable scope, expected output, current authorization and the next human-review stop. Delegation does not authorize generation/spend or external actions beyond that scope, and does not create new user-visible chats.

Report the current station, actual completed output, held reason and next action. A route map, prepared activation brief or inventory report is not an executed workflow.
